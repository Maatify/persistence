# تقييم مستقل — DG-03: الاستمرار بعد `1213` داخل معاملة المستدعي

> **⚠️ تصحيح (الجولة الثانية، F45-R03/R05):** (1) عبارة "`DO 0` يعمل على MySQL وMariaDB" كانت **تتجاوز الأدلة**؛ التجربة الأصلية على MySQL 8.4.10 فقط. الجولة 2 شغّلت التجارب على MariaDB 11.8.9 أيضًا (انظر أدناه) ولا تعمّم على إصدارات أخرى. (2) فُحص سؤال `autocommit=0` فعليًا وتبيّن أن `DO 0` **لا** يفتح معاملة جديدة ويعيد `inTransaction() = false` (على MySQL وMariaDB 11.8.9). (3) `DO 0` تحديث لحالة السائق وليس منعًا. التفاصيل والتوصية النهائية في [`ADDENDUM-2-F45-RESPONSE.md`](ADDENDUM-2-F45-RESPONSE.md).


**الحالة:** دراسة فقط. التجارب: [`dg03/experiments.php`](dg03/experiments.php) (مخرجاتها الخام [`dg03/experiments-output.txt`](dg03/experiments-output.txt))، على MySQL 8.4.10 بـ deadlock حقيقي بين عمليتين (نفس سقالة [`examples/deadlock-retry`](../../../examples/deadlock-retry)).

## 1. الظاهرة

عند `1213` يلغي InnoDB **المعاملة كلها** على الخادم، بينما `pdo_mysql` يظل يُبلغ `inTransaction() === true` حتى أول جملة ناجحة. كل ما يكتبه المستدعي بعد التقاط الاستثناء يُنفَّذ بلا معاملة (autocommit).

| التجربة | النتيجة |
|---|---|
| **E1** المستدعي يلتقط `1213` من `PdoDeadlockRetrySavepointTransactionRunner` ويكمل | `inTransaction()` = `true` مباشرة بعد الخطأ، ثم `false` بعد الكتابة التالية؛ `commit()` يرمي `There is no active transaction`؛ **المثبَّت فعليًا: `["caller-after"]` فقط، `caller-before` ضاع** |
| **E2** نفس الحالة + جملة `DO 0` فور الالتقاط | `inTransaction()` = `false` **فورًا قبل أي كتابة**؛ حارس المستدعي `if (!inTransaction()) abort` ينجح؛ لم يُثبَّت شيء |
| **E3** الجلسة على `autocommit=0` | الأسوأ: `inTransaction()` = `true` بعد الكتابة التالية، و`commit()` **ينجح بصمت** ويثبّت العمل اللاحق للـ deadlock فقط، فلا حتى استثناء إنذار |
| **E4** `1205` (lock wait timeout) بدل `1213` | المعاملة **حية**، الـ savepoint تراجع عن عمل الدالة وحده، عمل المستدعي السابق محفوظ، والمتابعة سليمة: `["caller-before","caller-after"]` |
| **E5** كشف اختفاء المعاملة | `SELECT @@in_transaction` غير موجود في MySQL (خطأ `1193`)؛ `DO 0` يعمل على MySQL 8.4.10 (وعلى MariaDB 11.8.9 في الجولة 2) ويصحح حالة السائق؛ و`@@in_transaction` موجود في MariaDB فقط |

**الخلاصة:** الخطر خاص بـ `1213` (وحده من أخطاء الحقل يُلغي المعاملة كلها). الـ savepoint يفي بوعده مع `1205`/`1062`/أخطاء النطاق، ولا يستطيع الوفاء به مع `1213`.

## 2. ما يمكن منعه داخل المكتبة وما لا يمكن

| الإجراء | ممكن داخل المكتبة؟ | الدليل / الحدود |
|---|---|---|
| **منع** كتابات المستدعي بعد `1213` | **لا.** الـ PDO ملك المستدعي والمكتبة لا تعترض جمله (ولا يجوز لها حقن PDO مغلَّف دون كسر عقد "المضيف يوفّر PDO"). | E1 |
| **جعل حالة السائق صادقة** فور `1213` (جملة `DO 0` في مسار التنظيف عند التقاط `PDOException` بـ `40001/1213` داخل معاملة المستدعي، بنفس منطق الاستخدام الحالي في `OwnedTransactionExecutor`) | **نعم، ضيق وغير كاسر:** لا استثناء جديد ولا تغيير في الاستثناء المنتشر؛ يتغير فقط أن `inTransaction()` يصير `false` بدل `true` الكاذبة. | E2: الحارس يعمل قبل أي كتابة |
| **كشف** حدوث الإلغاء داخل المكتبة نفسها | نعم (الفحص ذاته: `inTransaction()` الراكد + `DO 0` ← `false`)، وتقوم به المكتبة أصلًا لإعادة المحاولة المملوكة. | `OwnedTransactionExecutor::deadlockEndedOwnedTransaction()` |
| **استثناء مميِّز** (`PDOException` فرعي يطبّق `PersistenceException` مع علامة "المعاملة ألغيت") | ممكن تقنيًا (يحافظ على `catch (PDOException)`) لكنه **يغير عقدًا منشورًا** ("rethrows the exact original PDOException") وتختبره الاختبارات؛ يحتاج قرار Minor/توثيق. أقوى من الإصلاح السابق لكنه ليس ضروريًا لتحقيق السلامة. | مراجعة العقد |
| **إعادة محاولة** داخل معاملة المستدعي | **لا يجوز** (تعيد جزءًا من معاملة لا تملكها)؛ مرفوض في ADR 0004. | ADR 0004 |
| **تعطيل** `autocommit=0` أو فرض إعدادات جلسة | لا (إعداد المضيف) | E3 |

## 3. ما يجب إلزام المستهلك به (قواعد توثيق/معيار)

1. **`1213` قاتل لمعاملة المستدعي:** أي `PDOException` بـ `errorInfo[1] === 1213` يجب أن يُعاد رميه (أو يُحوَّل لإعادة محاولة على **أعلى** مستوى يملك المعاملة، مثل `PdoDeadlockRetryTransactionRunner` المحيط)، ولا يُلتقط ثم يُكمل العمل في المعاملة نفسها.
2. **لا تلتقط `Throwable`/`PDOException` بصورة عامة حول runner بنمط savepoint** ثم تتابع؛ التقط **الأخطاء المتوقعة بكودها** (`1062`، `1205`، استثناءات النطاق) واترك الباقي ينتشر.
3. إن كان لا بد من المتابعة بعد التقاط عام فاستخدم حارسًا: `$pdo->exec('DO 0'); if (!$pdo->inTransaction()) throw …;` (E2)، ولا تعتمد على `inTransaction()` وحدها (E1).
4. **تجنّب `autocommit=0`** مع هذه الأنماط: يحوّل الفشل الصامت إلى commit ناجح (E3).
5. الـ savepoint يعزل **أخطاء الجملة** لا إلغاء الخادم للمعاملة؛ لا يُقدَّم كحماية من deadlock.
6. إعادة المحاولة بعد `1213` = إعادة تنفيذ **المعاملة الخارجية كلها** عبر runner مالك (`maxDeadlockRetries > 0`) مع شروط الـ idempotency الموثقة.

## 4. الأثر على العقود والاختبارات والوثائق

- **لا حاجة لتغيير توقيع أو استثناء** لتحقيق جوهر الحماية؛ الإصلاح الوحيد المقترح داخل المكتبة (resync) تغيير سلوك مراقَب صغير (`inTransaction()` تصبح صادقة بعد `1213`).
- اختبارات مطلوبة إن اعتُمد: Regression يثبت أن `inTransaction()` = `false` بعد `1213` في مسار الانضمام وفي مسار الـ savepoint؛ مثال Consumer ثالث لـ `examples/deadlock-retry` يعرض E1/E2؛ وتعديل `02_caller_owned_no_replay.php` ليصرّح بعاقبة المتابعة.
- وثائق: README والمرجع و`PDO_TRANSACTION_ARCHITECTURE.md` تضيف قسم "ما بعد `1213`" (القواعد 1–6)، وتحذيرًا مجاورًا لوصف الـ savepoint ("معزول عن أخطاء الجملة، لا عن deadlock").
- معيار: يغذي SG-01 (سياسة deadlock/retry) بالقواعد 1–6 كمتطلبات لحزم المستهلكين.

## 5. التوصية الهندسية (واحدة)

**توثيق إلزامي (القواعد 1–6) + إصلاح ضيق داخل المكتبة يُصحّح حالة السائق بـ `DO 0` عند `1213` في مسارَي الانضمام والـ savepoint،** دون استثناء جديد ودون محاولة منع كتابات المستدعي (غير ممكن). الاستثناء المميِّز يبقى خيارًا لاحقًا غير لازم للسلامة.

**لم يُثبت:** MariaDB خلاف 11.8.9 (10.11 وغيرها)، MySQL 8.0 وغير 8.4.10، mysqlnd مقابل libmysqlclient، PHP غير 8.4، الوكلاء/Galera (قد يصل `1213` عند `COMMIT`).
